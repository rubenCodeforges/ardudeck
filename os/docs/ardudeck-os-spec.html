01Principles

The rules every feature is checked against.

  • Integrated, not a skin.Every feature lives in a real OS surface: the desktop layer, top bar, quick settings, lock screen, notifications, GNOME search, file associations, systemd services, native settings windows. Theming alone is never a feature.
  • Show only what is real.A widget row, gauge or menu item exists only while its data does: no receiver means no GNSS rows, no fix means no position or altitude, a locked SIM means no cellular row. Placeholders like "Not found" or "--" are not shown in status surfaces.
  • The OS works with the app closed.Vehicle link, telemetry, parameter cache, desktop instruments and alerts are system services. The ArduDeck app is one client among several.
  • The desktop app is the reference.Protocol code, mode tables, MAVFTP and gauge designs are shared from the monorepo (@ardudeck/mavlink-ts, @ardudeck/vehicle-core, @ardudeck/comms), never rewritten.
  • Off ArduDeck OS the app is unchanged.Every integration is detected at runtime and falls back silently on macOS, Windows and other Linux.
  • Never compete with the pilot.Background downloads and stream requests run only while the vehicle is disarmed and no GCS is attached.
  • One spec, two distros.Each component lists how it ships on Fedora and on Debian; manual steps on the tablet are recorded so the images can reproduce them.

05Ports and APIs

Contracts other components rely on. Change them only with a version bump.

14550/udp

Vehicle link

Default connection. ELRS backpacks, Wi-Fi bridges and forwarders send here. Bound on all interfaces.

14570/udp

GCS clients

Loopback only. Any datagram registers a client; vehicle traffic fans out to all clients.

14571/udp

App local port

Fixed source port of the ArduDeck app on the OS link, so reconnects keep their slot.

47801/tcp

Link API

/v1/info, /v1/vehicle, /v1/vehicle/params, /v1/links. Writes need X-ArduDeck: 1.

47800/tcp

Station API

/state: GNSS, LTE, Wi-Fi, batteries, heading, light.

14572/udp

Surface local port

Source port of the desktop surface instance on the OS link.

254 / 191

MAVLink identity

sysid 254, compid 191 for the service's own messages. Not 255, see decisions.

07Decisions

Why things are the way they are.

  • Service heartbeat uses sysid 254, not 255.ArduPilot's GCS failsafe tracks heartbeats from SYSID_MYGCS (255 by default). A 255 heartbeat from the OS could keep the failsafe from firing after the pilot's real GCS dies.
  • LAN broadcast discovery while no vehicle is live.Relays that learn their clients (the app's MAVLink forwarding, mavlink-router) never streamed until someone sent first, and dropped silent clients after 15 s.
  • Identity is re-learned on every reconnect.A different airframe on the same sysid was cached under the previous board's UID.
  • Parameters are fetched only while disarmed and with no client attached.Narrow links (ELRS) cannot carry a parameter download and live telemetry at once; a GCS that attaches takes over.
  • compid 191 for the service, 190 for the app.MAVFTP replies are routed by target component, so both can run sessions without stealing each other's replies.
  • One owner per GNSS receiver: the link service.stationd held the tablet's GNSS port and swallowed the replies to a MON-VER query; base configuration and RTCM need exclusive, coordinated access.
  • Listen before talking to unknown serial devices.GNSS modules and radios share USB bridge chips; writing probe bytes to a flight controller or radio is unsafe. Only proven GNSS ports get a UBX query.
  • vehicle-core has no dependencies.Importing one enum from the mavlink-ts root pulled the full generated registry into the app's renderer and slowed tests past 5 s.
  • Desktop instruments draw with Cairo in the shell.No extra process, works on the desktop layer, matches the app's gauge geometry. Maps and synthetic vision need a different surface, see roadmap.
  • os-release keeps ID=fedora.dnf, flatpak and toolbox key off ID; branding goes in VARIANT and PRETTY_NAME.

08Known issues

Open problems, most important first.

  • open Login screen (GDM) on-screen keyboard.Needs /etc/dconf/db/gdm.d/91-ardudeck-osk with screen-keyboard-enabled=true; root popup was dismissed, pending.
  • fixed Lock screen had no keyboard.GJS OSK switches GNOME's keyboard off while it runs and restores the value it saw at start; an unclean logout saved "off", so the lock screen (where user extensions stop) had none. The ArduDeck extension now also runs in the unlock-dialog session mode and switches GNOME's keyboard on whenever the screen locks; its widgets and the Vehicle Link tile exist only when unlocked.
  • open Lingering user manager keeps old group membership.With linger on, the user systemd manager survives logout, so dialout only applies to services after a reboot. GNSS stays unreadable until then.
  • open Release builds (now v0.1.2-rc8 in the menu) do not know the OS linkand would compete for UDP 14550 if set to listen there. A second launcher "ArduDeck (OS build)" runs the feat/ardudeck-os build. Merge the integration before the next release.
  • open USB device classes are by vendor ID only.Move KNOWN_BOARDS from the app into vehicle-core for board names.
  • open UDP peer connection not yet verified against a live forwarder.The Mac SITL was stopped during the test.
  • open Compass heading units on the HID sensor hub are inferred(raw / 1e5 degrees) and not yet checked against a real compass.
  • open Two existing tests time out on the tablet CPU(mavlink-parser truncation, workspace layouts under load). Not caused by OS work.

09Roadmap

Next, in order.

  • Desktop surface polish.Hide it from Alt+Tab; show the operator's own GNSS position and the station card inside it; tap targets that open the full app at that view; vehicle actions only via slide-to-confirm; consider a lighter WebKitGTK host instead of a second Electron.
  • Nested shell for testing(mutter-devkit, needs shell/mutter 50.0 → 50.5) so extension changes can be checked without logging out.
  • ModemManager ignore rule for flight controllers and radios.
  • Branding assets and system changes moved into os/with an install script, then mkosi configs for Fedora and Debian.
  • Armed-mode system state.No sleep, no updates, no notification noise while the vehicle is armed.
  • Drone files as first-class citizens acceptedOpen .bin/.tlog/.ulg/.param/.waypoints/.plan in the right ArduDeck view; file-manager thumbnails (flight track, mission route); GNOME search over live params, logs and missions.
  • Companions and second screens acceptedardudeck-agent companions announce over mDNS and appear under Detected in Vehicle Link, updatable from the tablet; QR pairing of the phone second screen; WFB-ng receiver as a system service with a video panel. Hardware not available yet for testing.
  • First boot and identity acceptedWelcome flow (connect vehicle, pair radio, Hangar sign-in, offline maps for the area); ardudeck CLI over the link API; vehicle status line on SSH login.
  • Offline packs acceptedMap tiles, terrain, firmware and docs as managed downloadable packs.
  • Hangar modules contributing desktop widgets deferredToo early; revisit once the module SDK settles.
  • Automatic log download, landing notifications, logbook rejected for nowLog download time depends on the link and logs may not exist; reconsider later.

10Test log

What has been proven and how.

  • ArduCopter 4.7.1 SITL on the tablet → os-linkd:1350 params via MAVFTP in 2.5 s; identity from AUTOPILOT_VERSION; telemetry streams requested when unattended.
  • Branch build of the app on the tablet:OS badge shown, opened connected via "ArduDeck OS link", 1350 params served from the cache (journal: served 1350 cached params).
  • SITL on a Mac with the app's MAVLink forwarding → tablet over a phone hotspot:found by discovery with no configuration, 1633 params via MAVFTP in 7.4 s, link stable after the keepalive fix.
  • Link API and settings:connection add / switch / master switch through the API; writes without the header rejected (403); Link Settings window rendered offscreen with live data.
  • GNSS detector:built-in receiver found without configuration and identified as u-blox NEO-M8N (SPG 3.01, GPS/GLO/GAL/BDS), position only; live fix 9 satellites, HDOP 0.91 on /v1/gnss.
  • Desktop surface:second app instance in surface mode attached to os-linkd (client 14572) and rendered the satellite map, mission line, instruments and synthetic vision for SITL flying a mission from the Mac (captured via DevTools).
  • Unit tests:vehicle-core 26, os-linkd 13, app OS integration 6; app suite otherwise unchanged.
